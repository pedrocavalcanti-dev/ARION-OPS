# ARION OPS 1.4.1 — Roteiro de Implantação Windows Server

Checklist operacional para atualizar a instância de produção Windows Server (`C:\Users\Arion\Desktop\ARION-OPS`) a partir da tag **`v1.4.1`**, em janela autorizada.

> **Nenhuma etapa deste roteiro foi executada automaticamente contra o servidor Windows Server ou MySQL de produção durante a publicação da tag `v1.4.1`.**

## 1. Pré-requisitos verificados da versão

- Python 3.12 com `.venv` na raiz do checkout.
- Node.js 24 (`package.json` declara `"build:production": "node frontend_src/build.mjs --production"`).
- Nenhuma dependência Python ou NPM adicional obrigatória além de `requirements.txt` / `requirements-prod.txt` e `package.json`.
- `.env` local de produção preservado na raiz (nunca sobrescrever nem expor segredos ou tokens DPAPI).
- Utilitário `mysqldump` disponível para a conta de serviço/operador no Windows Server.
- O servidor continuará usando suas próprias fontes locais/OTRS/CMDB; jamais copiar `db.sqlite3` de DEV para produção.

## 2. Backup obrigatório antes da atualização

Registrar o commit atualmente em execução no servidor e gerar backup consistente do MySQL antes de qualquer alteração de código ou schema:

```powershell
Set-Location 'C:\Users\Arion\Desktop\ARION-OPS'
git rev-parse HEAD
git describe --tags --always

# Backup MySQL fora do diretório do projeto (arion-backups)
.\deploy\windows\backup-arion.ps1
```

## 3. Parar Web e Worker com segurança

```powershell
.\deploy\windows\stop-arion.ps1 -Role worker
.\deploy\windows\stop-arion.ps1 -Role web
.\deploy\windows\status-arion.ps1
```

Confirmar que os processos Python de `web` e `worker` encerraram antes do `git pull` / `git checkout` e do build estático.

## 4. Atualizar código para a tag `v1.4.1`

```powershell
git fetch origin --tags
git status --short
# Atualizar para v1.4.1 em fast-forward / checkout da tag (sem descartar alterações locais inesperadas sem revisão)
git checkout main
git pull --ff-only origin main
git checkout v1.4.1
git rev-parse HEAD
```

## 5. Atualizar dependências e gerar build de produção

Executar o build frontend **antes** de `collectstatic` para que os 36 bundles de produção e o Service Worker versionado com `1.4.1` estejam presentes:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-prod.txt
npm ci
npm run build:production
```

## 6. Migrations e sincronização de permissões (`bootstrap_access`)

Aplicar as 8 migrations aditivas (`cancelamentos.0007`, `configuracoes.0012`, `integracoes.0017–0021`, `qualidade.0016`) e garantir a sincronização explícita das novas permissions no grupo existente **`Administrador do Sistema`** (Adendo 2 — corrige a ausência do botão **Apresentar** em produção):

```powershell
$env:ARION_ENV = 'production'
.\.venv\Scripts\python.exe .\arion_geo\gerenciar.py showmigrations --plan
.\.venv\Scripts\python.exe .\arion_geo\gerenciar.py migrate --plan
.\.venv\Scripts\python.exe .\arion_geo\gerenciar.py migrate --noinput
.\.venv\Scripts\python.exe .\arion_geo\gerenciar.py bootstrap_access
```

Conferir no banco (somente leitura) que `Administrador do Sistema` possui `configuracoes.present_geo` e `qualidade.delete_qualityorder`:

```powershell
.\.venv\Scripts\python.exe .\arion_geo\gerenciar.py shell -c "from django.contrib.auth.models import Group; g = Group.objects.get(name='Administrador do Sistema'); print('present_geo:', g.permissions.filter(codename='present_geo').exists(), 'delete_qualityorder:', g.permissions.filter(codename='delete_qualityorder').exists())"
```

Atribuir manualmente `configuracoes.present_geo` em **Configurações → Grupos e acessos** para outros perfis (como `Gestor`, caso desejado), já que o `bootstrap_access` não altera permissões de grupos não administrativos já existentes.

## 7. Static, checagens de produção e validação pré-start

```powershell
.\.venv\Scripts\python.exe .\arion_geo\gerenciar.py collectstatic --noinput
.\deploy\windows\production-check.ps1
.\.venv\Scripts\python.exe .\arion_geo\gerenciar.py check
.\.venv\Scripts\python.exe .\arion_geo\gerenciar.py makemigrations --check --dry-run
```

Confirmar também em `configurações → GEO / Integrações` as fontes IBGE e meteorológicas autorizadas (lembrando que produção regular com Open-Meteo deve respeitar licença comercial/endpoint próprio configurado pelo responsável, sem acoplamento automático à API pública caso não autorizada).

## 8. Reiniciar serviços e validar em operação

```powershell
.\deploy\windows\start-arion.ps1 -Role web
.\deploy\windows\start-arion.ps1 -Role worker
.\deploy\windows\status-arion.ps1
```

Checklist pós-subida em produção:

1. Abrir `/configuracoes/sobre/` ou `/configuracoes/documentacao/atualizacoes/` e confirmar **v1.4.1** carregada e Service Worker atualizado para `1.4.1` (se houver cliente em sessão antiga, aguardar/aceitar o aviso de atualização do PWA ou forçar reload limpo).
2. Validar as principais rotas autenticadas sem HTTP 500: `/painel/`, `/dashboard/`, `/cockpit/`, `/mapa/`, `/rankings/`, `/base/`, `/qualidade/`, `/cancelamentos/`, `/configuracoes/`.
3. Com usuário membro de `Administrador do Sistema` (não superusuário) que possua `configuracoes.present_geo`, verificar a exibição do botão **Apresentar** em `/mapa/`.
4. Abrir o drawer lateral de UF no `/mapa/` e no Modo Apresentação e validar a aba **Chamados** (listagem paginada/buscável, visível somente para quem possui `view_operational_tickets` e sem campos internos na apresentação) e o posicionamento sem colisão com o cabeçalho superior.
5. Conferir logs em `var\logs` do Web e Worker após os primeiros minutos de operação.

## 9. Referências complementares e rollback

- Detalhes da entrega: [Versão 1.4.1](v1.4.1.md).
