# ARION OPS 1.4.0 — Checklist futuro de implantação Windows

**Procedimento preparado, não executado nesta entrega.** Requer janela e autorização próprias. O destino atual é Windows Server, MySQL e supervisor Web/Worker existentes. Linux/Docker não faz parte deste procedimento.

## Preparar antes do corte

- Registrar revisão instalada, versão exibida, migrations aplicadas e contagens de dados próprios do servidor. Não presumir que a identificação 1.3.1 determine o commit ou o schema efetivamente instalado.
- Fazer backup MySQL consistente com `deploy/windows/backup-arion.ps1`, para diretório privado externo ao projeto, e verificar sua restauração em ambiente isolado. Preservar usuários, grupos, escopos, Qualidade, auditoria, integrações e registros operacionais existentes.
- Fazer cópia privada da configuração, `.env`, certificados, storage privado e arquivos de supervisor. Preservar ACLs e conta Windows; não usar credenciais/DPAPI do DEV como substitutos.
- Conferir Python da `.venv`, dependências dos lockfiles, Node 24 e MySQL. Validar recursos de timezone do MySQL usados nas agregações Django e acesso de escrita somente ao schema autorizado. Não imprimir senhas ou URLs completas.
- Conferir a [auditoria documental e pendências reais](v1.4.0-auditoria-documental.md), o [guia do servidor](../02-arquitetura/implantacao-e-producao.md) e a [administração diária](../03-seguranca-e-qualidade/administracao-operacional.md). A política de 90 dias foi informada como já ativa no servidor conhecido: consultar o estado, **não reativar globalmente no deploy**. Rever grants de Relatórios e gestão de contatos antes de ampliar acessos.
- Diretório `C:\Users\Arion\Desktop\ARION-OPS`, domínio `https://nocatacadoarion.bicoai.com.br/` e loopback 8100 são referências informadas da implantação, não constatadas remotamente nesta revisão. Validar contra `.env`/ambiente, tarefas e ingress sem expor segredos. O default de porta do código é 8000.

## Atualizar código e schema, em janela autorizada

Na raiz do checkout do servidor, após revisar backups e o plano de retorno:

```powershell
git status --short
git fetch origin --tags
git log --oneline HEAD..origin/main
```

Interromper se houver trabalho local não reconciliado ou divergência. Não usar reset destrutivo ou push forçado. Selecionar a revisão aprovada para o corte; mudanças posteriores em main exigem nova revisão.

```powershell
.\deploy\windows\stop-arion.ps1 -Role worker
.\deploy\windows\stop-arion.ps1 -Role web
git pull --ff-only origin main
.venv\Scripts\python.exe -m pip install -r requirements-prod.txt
npm ci
npm run build:production
# Build antes de carregar Django: produção exige manifest de frontend válido.
.venv\Scripts\python.exe arion_geo\gerenciar.py check
.venv\Scripts\python.exe arion_geo\gerenciar.py showmigrations --plan
.venv\Scripts\python.exe arion_geo\gerenciar.py migrate --plan
```

Revisar o plano. O intervalo documental desde `2fc4c34` contém Autenticação `0001–0002`, Cancelamentos `0001–0006`, Configurações `0010–0011` e Integrações `0015–0016`. O executor Django determina as dependências e quais realmente faltam.

```powershell
.venv\Scripts\python.exe arion_geo\gerenciar.py migrate --noinput
.venv\Scripts\python.exe arion_geo\gerenciar.py collectstatic --noinput
.venv\Scripts\python.exe arion_geo\gerenciar.py check --deploy
.venv\Scripts\python.exe arion_geo\gerenciar.py makemigrations --check --dry-run
.\deploy\windows\production-check.ps1
```

O build cria bundles e manifest locais; não copiar os bundles antigos do DEV. O catálogo central atualiza a versão/PWA quando o código aprovado for implantado e o processo reiniciar, não por alteração manual de HTML.

## Carga histórica separada de Cancelamentos

**Git e migrations não levam os 162 processos do SQLite DEV para o servidor.** Não restaurar o SQLite inteiro sobre o MySQL existente, não usar `migrar_banco_arion --full-snapshot` para mesclar bases e não apagar dados atuais do servidor.

1. Obter extração autorizada consistente das cinco tabelas ArionBroker, schema/dicionário e relatório mais recente; transportar em diretório privado com checksum, datas/fuso e identificação do marco de corte. Excel/CSV complementar só participa quando houver correspondência confiável.
2. No MySQL de ensaio com cópia autorizada do contexto do servidor, revisar mapeamentos de TicketID/Ticket#, CI, pessoas históricas, PKs legadas e cardinalidade. Resolver duplicidades por origem/entidade/PK e TicketID comprovado; não por título semelhante.
3. Executar preview/dry-run **em ensaio DEV MySQL permitido**, com validação de totais/filhos/conflitos pelo [importador existente](../05-funcionalidades/cancelamentos-migracao-arionbroker.md). Todos os modos do comando bloqueiam produção. Manter responsáveis Django atuais independentes, nomes históricos como evidência e valores NULL/zero preservados. Seguir o [roteiro específico de carga produtiva](../06-integracoes-e-dados/arionbroker/carga-producao.md), que identifica a implementação ainda necessária.
4. **Bloqueio atual:** `importar_cancelamentos_legado` exige DEV e schema `arion_geo_dev`; Apply em produção não é liberado nesta release. Preparar, em tarefa autorizada própria, o modo seletivo de produção com allowlist do destino, ator autorizado, dry-run aprovado, backup/restauração e lote transacional. Não executar com `ARION_ENV=development` para contornar esse bloqueio.
5. Somente após essa preparação e homologação, aplicar o lote em janela controlada. Exigir `extraídos = novos + já conciliados + conflitos + inválidos`, sem categorias sobrepostas, conferir totais por etapa/período e histórico, manter mapa de origem/checksum, repetir o preview para comprovar zero duplicidade e verificar a recuperação por lote.
6. Atualizações posteriores de filas/pendências/valores devem ser conciliadas contra a fonte mais recente, preservando o snapshot original e alterações locais. Conclusão histórica não fabrica aprovação atual, pagamento ou confirmação ISP. Não disparar notificações, escrita OTRS/CMDB ou mudança de status de link.

Se o código precisar ser liberado antes da carga autorizada, o módulo mostrará somente os processos oficiais já presentes no servidor. Não preencher telas com contagens fixas para reproduzir o DEV.

## Recuperação

Interromper tráfego/escritas antes de recuperar. Preservar banco e logs da tentativa, comparar o que foi gravado desde o corte e voltar ao código conhecido compatível com o schema. Restore de MySQL/configuração só com o backup verificado e o plano aprovado; reverter Git sozinho não desfaz migrations nem dados. `rollback_banco_arion.py` troca conexão e não é recuperação do MySQL nem importador do histórico. Não ativar o SQLite DEV como banco de produção. Reconciliar alterações posteriores ao backup antes de retomar a operação.
