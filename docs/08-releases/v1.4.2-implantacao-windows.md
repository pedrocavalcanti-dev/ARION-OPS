# ARION OPS — Roteiro de implantação Windows Server (`v1.4.2` candidata)

Roteiro operacional para atualizar o servidor Windows de produção em `C:\Users\Arion\Desktop\ARION-OPS` (MySQL local + Waitress + `integration_worker`).

> **Importante:** Este roteiro utiliza apenas scripts verificados em `deploy/windows/`. Não altera tags oficiais (`v1.4.0` e `v1.4.1` permanecem intactas) e não executa migração Linux/Docker.

## Recuperação da implantação interrompida em `e60a4fc`

O servidor já recebeu dependências, as seis migrations, bootstrap de acesso, reconciliação CMDB e snapshot. **Não repetir essas etapas para aplicar esta correção.** A publicação parou depois do collectstatic, nos três controles de JavaScript. Esta seção substitui o roteiro de implantação completa para esse estado específico.

Causas confirmadas no código:

- **Referências JS:** build reconhecia `arion_js` e `arion_bundle_js`, mas production-check reconhecia só `arion_js` e comparava com um manifest que também inclui `__service_worker__`. Entradas omitidas pelo checker: `cancelamentos/dashboard.js`, `qualidade/shell.js`, `qualidade/guide.js`, `qualidade/dashboard.js`, `qualidade/lists.js` e o worker. `plant-history.js`, `contacts.js` e `base-links-identity.js` usam corretamente a tag; um manifest anterior ao build atualizado pode adicionalmente estar desatualizado.
- **Fontes em STATICFILES_DIRS:** `static/js/integracoes/brevo.js`, `static/js/qualidade/{archive,checklist,monitoring}.js` e `static/pwa/service-worker.js` ainda eram coletáveis. `static/vendor/echarts/echarts.min.js` é distribuição pública legítima e era falso positivo. Staging oculto de build interrompido não é coletado pelo ignore padrão do Django.
- **Fontes em STATIC_ROOT/js:** os quatro scripts próprios eram publicados porque seus templates ainda usavam `{% static %}`. Após a migração, uma coleta sem `--clear` não remove arquivos antigos. O checker continua recusando esses resíduos e também o antigo worker legível.

Correção: fontes movidas sem reimplementar módulos, templates usando o pipeline existente, build determinístico com seed fixa, checker reconhecendo as duas tags e o worker reservado, exceção exata para ECharts. Fontes próprias adicionais, referências ausentes, bundles inexistentes e source maps continuam causando falha. Admin e bibliotecas necessárias permanecem publicados.

```powershell

Conferir requests JS sem 404 e logs Web/Worker sem tracebacks. A versão pública continua `1.4.1` até homologar a candidata.

Se qualquer etapa falhar, consultar `status-arion.ps1` e logs, corrigir a causa e repetir a validação; não iniciar se production-check falhar. Banco migrado não deve ser restaurado nem ter migrations repetidas automaticamente. Não fazer rollback isolado de código para um schema incompatível. ## Segurança da próxima atualização completa

`manage-arion.ps1 -Action Update` é o orquestrador existente. Agora compila frontend e faz preflight antes da parada; backup pré-migration continua obrigatório quando houver plano aprovado. Coleta limpa e production-check completo precedem o start, seguido de verificação HTTP. Em falha, registra Web/Worker e orienta recuperação, sem restore de MySQL nem start automático com assets inválidos. O checkout é atualizado pelo mecanismo existente; isto não é uma implantação atômica com diretório de staging separado.

Para uma implantação completa manual, executar build/preflight antes da parada sempre que possível. O roteiro abaixo é para servidor ainda não atualizado; não repeti-lo no servidor já migrado.

## 12. Checklist de homologação pós-deploy

1. **Dashboard (`/dashboard/`):**
   - Conferir card **Base CMDB** (Total cadastrado, Ativos, Cancelados, data de referência).
   - Clicar em **Analisar planta** e validar as 3 abas (**Visão geral**, **Evolução histórica**, **Comparação por período**) nos temas claro e escuro.
2. **Cockpit (`/cockpit/`):**
   - Aplicar filtro de período/projeto/UF, clicar em **Planta × Chamados** e confirmar sincronização de filtros e paridade de números com o Dashboard.
3. **GEO Inteligência (`/mapa/`):**
   - Conferir paridade de incidentes válidos, links afetados e reincidentes entre Modo Normal e Modo Apresentação (ex.: Vivo / Bradesco).
4. **Qualidade (`/qualidade/`):**
   - Abrir **Ver estabilizados** (`/qualidade/estabilizados/`).
   - Conferir níveis **R1–R5+** nas Ordens de Qualidade.
   - Validar acesso de `Administrador do Sistema` e `Gestor` no cadastro/edição de **Contatos** (`/qualidade/contatos/`).
5. **Base (`/base/nao-identificados/`):**
   - Conferir carregamento da Central de Não Identificados, filtros e auditoria.
6. **Cancelamentos (`/cancelamentos/dashboard/`):**
   - Conferir que `Multa + Equipamentos + Outros = Total consolidado`.
7. **Logs operacionais:**
   - Inspecionar `var\logs\arion-web.log` e `var\logs\arion-worker.log` por 2–3 minutos sem tracebacks ou falhas de sincronização.

## 14. Procedimento de rollback

Em caso de anomalia crítica, registrar commit, migrations aplicadas, backup e estado dos serviços. Consultar o [procedimento de recuperação](../02-arquitetura/implantacao-e-producao.md). Interromper Web/Worker de forma controlada se necessário:

```powershell
.\deploy\windows\stop-arion.ps1
.\deploy\windows\status-arion.ps1
```

Não reverter apenas o Git sem avaliar compatibilidade com o schema já migrado. Não executar restore automático do MySQL nem migrations reversas. Restore, quando autorizado e necessário, exige destino e backup validados e reconciliação das alterações posteriores. Para o incidente de assets em `e60a4fc`, usar a recuperação do início deste roteiro, mantendo banco e código atualizados. Somente iniciar após o production-check e confirmar processos, HTTP e acesso autenticado.
